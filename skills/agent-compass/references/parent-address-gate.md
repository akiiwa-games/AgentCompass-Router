# Parent addressing and worker questions

The spawn gate prevents accidental unrouted launches. It is not a security boundary against a session that
deliberately disguises a launch: it judges the program each simple command of a shell line runs (seen through
interpreters and wrappers), and a line it cannot parse or a program that is not a literal is not a launch.

- Failure: an unaddressed worker cannot reach its coordinator; UI questions (including `request_user_input_async`) strand the workflow in the worker session.
- Action: refuse dispatch without an actual parent ID; refuse interactive user-question calls by an identified worker. Reads, repairs, messages and main-session questions remain allowed.
- Decision: use the launching session's host ID, include it and its messaging address in the delivered assignment, and preserve parentage in host metadata. Never substitute `top-level`, a task ID or the worker's own ID. Paseo resolves the parent before creation; native host orchestrators must carry the coordinator session ID plus its live inbox address and preamble.
- Recovery: obtain the actual parent from the host (`PASEO_AGENT_ID`, or the native host session ID and inbox address), supply it to `roll`, then deliver `worker_prompt_file` unchanged with the assignment. Workers send questions through the parent messaging channel.
- Degradation: missing parent information prevents launch. Missing worker-role evidence alone does not block a main-session question. Failed delivery after launch returns `BLOCKED / needs_input` through the existing result channel; it never permits a local question UI.
- Coverage: local hooks enforce questions for Paseo-labelled workers and CLI workers marked by the router. Native host preambles carry the same rule; runtime enforcement there depends on the host exposing worker identity to its hook.

## Completion-notification gate contract

- **Failure:** disabling completion notifications can lose the result of a worker without messaging tools.
- **Action:** block only `send_agent_prompt` with explicit `notifyOnFinish: false` from a parent to its own worker, including statically parsed wrapper calls.
- **Decision:** the hook's caller ID must equal the target's locally persisted `router.parent_id` / `paseo.parent-agent-id`; conflicting labels do not prove ownership. No network lookup is needed.
- **Recovery:** set `notifyOnFinish: true` or omit the parameter. Worker-to-parent questions and final reports remain allowed with `false`.
- **Degrade:** missing caller identity, missing/unreadable target records, ambiguous ownership or dynamic wrapper arguments leave this check open; other router checks still apply.

## Disabled-target, quota and context-rotation gate contract

The gate governs dispatch: a launch, and a parent handing more work to its own worker. It does not govern communication between sessions, and host policy (`allowed_accounts`) is not a gate condition: it says which accounts the router chooses by itself.

- **Failure:** launching a native sub-agent that the router did not hand to the caller; launching new work on a model the user unchecked in model management without the user naming that route, on an account with leftover meter fields or on a quota-exhausted window; launching natively on the authority of a project rule (`hard_constraint`) that overrides one machine's choice to keep an account out of automatic routing; handing another turn to one's own worker on an exhausted window, or one at or above the configured context rotation threshold (`rotate_after_carried_tokens`, set in the tray) in historical uncompressed tokens.
- **Action:** block native sub-agent launches (Claude Code `Agent`/`Task` except built-in tool agents, Codex `spawn_agent`, Antigravity `invoke_subagent`, T3 `delegate_task`, shell `orca orchestration worker-start` / `orca agent launch` / `run_dot_task.py`) unless authorized for this caller as below. Block new launches on an unchecked model unless the launch's authority is a `user_override` decision (a bound launch: the decision behind its `router.dispatch_id`; a native launch: its consumed `native` hand-over or matched standalone `record` row; Workflow, schedules and unbound `create_agent` launches never are). A native sub-agent (Claude Code `Agent`/`Task`, Codex `spawn_agent`) runs on the calling session's own account: a launch that names a model and no provider or account resolves to that account when discovery records it (the one account of the family whose home is the directory the session's `CLAUDE_CONFIG_DIR` / `CODEX_HOME` names) for the checkbox rule above only, and its refusal names the model the launch asked for, that account and the matched route; every quota, window, floor and cooldown check on a native launch resolves the launch as it is written. Also block launches on an account with leftover meter fields or a quota-exhausted target, and a native launch whose matched `record` row is a project rule (`hard_constraint`, `dot_closed_loop`) carrying `host_policy_violation`. Block a parent's new turn to its own idle or unknown-state worker only for facts: leftover meter fields on its account, a quota window it draws that refuses a launch, or the rotation limit. Not blocked: a message to an agent the caller does not own (a peer, a session the user opened, a worker of another parent, an agent without labels, an ancestor), control messages to the caller's own running worker, and a turn to the caller's own worker on an account outside `allowed_accounts` or a model unchecked since its launch: continuing a worker that exists is not the router choosing that account or model. Completion-notification checks remain unchanged.
- **Decision:** a native sub-agent launch is authorized by one of two facts recorded by the writers, and by nothing else: (1) `roll` answered with a native hand-over (`dispatch_mode: "native"`, `caller_action: "launch_with_native_host_tool"`) recorded in `dispatch.sqlite3` (`dispatches`, `native_handover: true`) for this caller (matched against the caller's session/parent ID — a call carrying no session ID matches no named hand-over) matching the launch's resolved provider/account/model/effort, which has not yet been used and is atomically consumed (`claim_native_handovers`, after every check across the whole tool call has passed, idempotent on retries of the same host tool-call ID) by the launch it authorizes; or (2) a recent standalone `record` row (`stage: "record"`, within 15 minutes, not `--trigger workflow`, not `explicit_resume`, and not a decision owned by `roll` in `dispatch.sqlite3`) of this session matching the launch's resolved provider/account/model/effort. Unlike a one-use native hand-over, a standalone `record` row is not consumed on use and keeps authorizing matching native launches of its session throughout its 15-minute window, while a `record` written in a bare shell without a session ID carries no session restriction and remains eligible for matching launches without a conflicting session ID during those 15 minutes. Each host's unnamed model/provider is decided from the facts the call carries and never treated as a wildcard: Claude `Agent`/`Task` requires a `claude`-family route (and the session's recorded Claude account when discovered) and resolves an omitted/`inherit` model from custom `.claude/agents/*.md` frontmatter, `"haiku"` for built-in `Explore`, or explicit session `model` (requiring `model` otherwise); Codex `spawn_agent` requires a `codex`-family route (and its discovered account) and resolves an omitted `model` from Codex's top-level hook `model`; Antigravity `invoke_subagent` requires `antigravity` and resolves omitted/`inherit` `Model` from top-level `modelName` (when concrete, not `auto`) or matches `flash`/`flash_lite`/`pro` to their Antigravity tiers; multi-provider orchestrators (`delegate_task`, `orca`) must name both provider and model explicitly. A `plan` row is never worker launch authority (`plan` rows authorize only Paseo `create_schedule` / `update_schedule` in the session that ran `plan`). Ownership for turns is the completion-notification test: every nonempty locally persisted `router.parent_id` / `paseo.parent-agent-id` of the target must name the caller, and the target is not the caller itself. A label names the caller when it equals one of the caller's identities (the calling Paseo agent ID from the payload or `PASEO_AGENT_ID`, and the host session ID from the hook payload or `OWN_SESSION_ID_VARS`), or names a Paseo agent whose local record runs that host session (`persistence.sessionId` / `runtimeInfo.sessionId`). A caller with none of these, or labels that name another session, proves nothing, and the turn is communication. The caller's own worker is running when its local Paseo record says `lastStatus: running` (or `status: running` when present); an explicit current non-running `status` takes precedence, and `activeTurn` alone, tool arguments and prompt wording do not prove a running turn. Whether a ledger row carries a route (for standalone `record` rows, `Workflow`, and schedule `plan` rows) is decided on `stage` in `("plan", "record")` and a `bundle` naming `provider`, `account` and `model` (`bundle.bundle_id` resolves catalog launch fields such as `launch_model` when present). A launch's host-policy standing is decided on the fact that the matched `record` row carries `host_policy_violation` (which `record` writes from `host_policy.account_allowed` only on constraints other than `user_override`; a `user_override` row never carries it and is launch authority). No network lookup is required.
- **Recovery:** for an unauthorized native launch, run `agentcompass roll --brief <task.md>` (if `roll` returns `status: launched`, the worker is already running—do not invoke a native launch tool; if the host has no automatic launcher, `roll` returns `status: native` with a one-use hand-over; if the gate allowed a native launch and the host or user subsequently declined/cancelled the tool call, that hand-over was already spent at allow time and rolling again issues a fresh one), or run `agentcompass record` first for a forced launch the router cannot perform. While the owned worker is running, send a control message with completion notifications enabled. Otherwise collect its existing output, use `cancel_agent` if necessary, write a handoff and run `agentcompass roll --brief <handoff.md>`. A launch on an unchecked model: roll among the checked ones, or, when the user named this model in this request, pass `--provider/--account/--model --basis` to `roll` or `record --constraint user_override --basis "<the user's words>"`; checking it again is the user's choice in model management. Leftover meter fields: `agentcompass setup` removes them. A launch refused for `host_policy_violation`: if the user named this route in this request, record it with `--constraint user_override --basis "<the user's words>"`; otherwise roll without naming a route. An over-limit worker still requires rotation.
- **Degrade:** unreadable or write-locked `dispatch.sqlite3` or unreadable `router-ledger.jsonl` authorizes no launch (all native registry reads and hand-over claims fail closed with a bounded 0.5 s timeout, never falling into `evaluate_payload`'s allow catch-all or waiting 10 s on a write lock; built-in tool agents and non-launch tools do not touch the registry). An unconsumed native hand-over is bounded by `dispatch_registry.MAX_LIFETIME` (24 hours, `hard_until`) so a hand-over abandoned by a crashed or closed session cannot remain open indefinitely, while its workspace writer lock still lapses after `PREPARE_LEASE` (5 minutes) until consumed (`RUN_LEASE`, 10 minutes). A caller carrying no session ID matches no named `status: native` hand-over; for standalone `record` rows (section 6), when one side carries no session ID (e.g. a CLI `record` run in a bare shell), non-conflicting `record` routes remain eligible below any session-matched candidate. A native launch whose own account is not recorded (no discovered account with that home, more than one, another harness) or whose raw tool call names no model resolves to no account for `launch_target` when the model alone does not identify one, so the checkbox is not checked on an unrecorded account: the gate does not guess the caller's account. Missing caller identity, missing or unreadable target records and conflicting ownership make a turn communication, so it passes: the gate does not refuse on a guess. An unreadable fleet resolves no account or bundle and refuses nothing. Local `lastStatus` is the persisted snapshot, not an atomic daemon guarantee: status can change between the hook and message delivery, and offline records can be stale. Without a structured steer-only API this hook cannot eliminate that race; do not infer liveness from timestamps or message keywords. The session proof assumes one Paseo record per provider session: two records sharing one `persistence.sessionId` would both prove that session. A check the gate could not make (the fleet or a quota read that throws, a shell command line that parses in neither dialect, an exception inside the decision, stdin that is empty or not a JSON object) stays open as above, and the allow says so, naming the check and the error's type, never its text. Where the word goes: Claude Code and Codex, a `systemMessage` beside the allow (a field of their hook output for every hook, shown to the user); Antigravity, the optional `reason` of the PreToolUse answer (documented as the explanation shown to the agent or to the user; not run against Antigravity, so what it shows beside an allow is not established); Pi, a line on stderr that the generated extension shows with `ctx.ui.notify` where Pi has a UI (TUI, RPC) and writes to its own stderr in print and JSON mode, where UI methods are no-ops. The code of a code-mode tool is not a shell command line and never gets the notice. A crash inside the decision is an allow with exit 0 and the word on every host (it was an uncaught exception and exit 1: non-blocking by the documentation of Claude Code and Codex and by the Pi extension, except on Claude Code for Windows without Git Bash, where it blocked; Antigravity's documentation does not say). A recorded quota failure's refusal names the account, the recorded windows the launch draws and the command that clears the record, and says what lifts it: a newer successful usage reading that shows the window under 100% used or past its reset time; time alone never does.

What this leaves ungoverned: a session can feed work to an idle agent it does not own, on any account, without a check. That agent's account, quota and context are its own parent's or the user's to watch, the message is visible in both sessions, and no loss from it has been observed; a check would need a notion of "work" in a message that the gate cannot read from a prompt.
